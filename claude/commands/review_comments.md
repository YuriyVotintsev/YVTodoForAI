# Обработка review-комментариев

Комментарии лежат в `.ai-review-comments.json` в корне проекта. Их пишет пользователь в Rider через плагин YVTodoForAI:
к выделенному коду, к строке, к файлу, к папке, прямо в diff ветки или коммитов, либо общие.

Работа идёт **в две фазы: сначала все вопросы, потом вся работа**. Пока у открытых комментариев есть хоть один
вопрос без ответа — код не меняешь.

## Поля комментария

- `filePath` — путь от корня проекта (файл или папка); `null` — общий комментарий без привязки к коду.
- `startLine` / `endLine` — строки (с 1, включительно); `null` при заданном `filePath` — комментарий ко всему файлу/папке.
- `selectedText` — что было выделено; по нему ищи место, если строки съехали.
- `revision` — коммит, к которому относятся номера строк. `null` — рабочая копия на момент комментария.
  Если задан — смотри `git show <revision>:<путь от корня репозитория>`. Корень репозитория может быть выше корня
  проекта: `git rev-parse --show-toplevel`.
- `diffRange` — `<base>..<target>`, если комментарий написан в diff (`WORKTREE` — незакоммиченное состояние).
- `diffSnippet` — выделенный кусок diff (` ` контекст, `-` удалено, `+` добавлено). Комментарий к строкам с `-` —
  это про удалённый код (`revision` = база).
- `comment` — просьба об изменении или вопрос пользователя.
- `status` — `PENDING` | `IN_PROGRESS` | `HAS_QUESTIONS` | `DONE` | `CANCELED` | `CLOSED`. `CLOSED` ставит только
  пользователь, когда проверил выполненное, — такие комментарии не трогай.
- `questions` — твои вопросы: `{"question", "options", "answer"}`. Пользователь может ответить прямо в IDE.
- `thread` — переписка под комментарием: `{"author": "user" | "claude", "text", "at"}`. Сообщения пользователя — это
  уточнения к комментарию, отвечай на них там же.

Статус и переписку меняй через `~/.claude/scripts/ai_review.py`, а не правкой JSON руками:
`python ~/.claude/scripts/ai_review.py say <id> [СТАТУС] <<'EOF' … EOF` — сообщение пользователю (и статус),
`… status <id> СТАТУС`, `… show <id>`, `… open`. Поле `questions` при необходимости правь через Edit.

## Фаза 0. Подготовка

1. Прочитай `.ai-review-comments.json`. Нет файла или нет комментариев в `PENDING` / `HAS_QUESTIONS` — скажи об этом
   и закончи.
2. Заведи todo list: по пункту на каждый открытый комментарий.

## Фаза 1. Разбор и вопросы — код не трогаешь

Иди по открытым комментариям **строго по одному**: собери контекст только для текущего, реши, запиши в JSON, переходи
к следующему. Контексты разных комментариев не смешивай.

1. **Найди место.** Прочитай файл и сверь код со `selectedText`. Не совпадает — найди, куда код переехал (с помощью
   `revision` / `commitHash` и `git show`). Очевидное перемещение принимай молча. Код удалён или переписан так, что
   непонятно, к чему относится комментарий, — это вопрос.
2. **Пойми, что это.**
   - Просьба об изменении и понятно, как сделать (даже если это крупный рефакторинг) — вопросов нет, запиши план в todo.
   - Вопрос пользователя («зачем тут…», «почему так…») — разберись и ответь в переписке (`say`). Если из ответа
     следует, что что-то стоит поменять, задай вопрос «менять ли и как».
   - Несколько разумных вариантов, не хватает информации или непонятно, чего хотят, — вопрос.
3. **Вопросы** записывай в `questions` с вариантами в `options` (`answer: null`) и ставь статус `HAS_QUESTIONS`.
   Если в `questions` уже есть ответы (пользователь ответил в IDE) — используй их и повторно не спрашивай.

Когда прошёл все комментарии:

1. Есть вопросы без ответа — задай их через AskUserQuestion. Каждый вопрос отдельно, не объединяй похожие в один
   обобщённый: пользователь может захотеть разные решения. Ответы записывай в `answer` дословно.
2. Ответ «отменить» / «не надо» — статус `CANCELED` и короткое сообщение в переписке. Без согласия пользователя
   `CANCELED` не ставь.
3. Ответы могут породить новые вопросы — повторяй, пока у открытых комментариев не останется ни одного вопроса без
   ответа.

## Фаза 2. Работа

1. Определи порядок: сначала то, от чего зависят другие комментарии (например, «убери X из интерфейса» раньше, чем
   «измени тип X»).
2. Выполняй по одному: `status <id> IN_PROGRESS`, сделал — `say <id> DONE` с одной-двумя фразами о сделанном
   (файлы, методы). Отмечай пункт в todo.
3. Комментарий-вопрос, по которому ничего менять не нужно, — `DONE` с ответом в переписке.
4. Если по ходу работы всплыл вопрос, без которого нельзя продолжить, — `HAS_QUESTIONS` с вопросом, продолжай
   остальные, а в конце задай его и доделай.
5. После всех правок проверь сборку так, как принято в проекте (в Unity-проекте — скилл `recompile`, если он есть).
6. В конце коротко отчитайся: комментарий → что сделано; отдельно — что отменено и почему.

## Правила

- Никогда не коммить и не пушь.
- Никогда не предлагай «отложить на потом» или «обсудить позже» — всё решается здесь и сейчас.
- Не удаляй комментарии. Меняй только `status`, `questions` и переписку, остальные поля не трогай. Незнакомые поля
  сохраняй.
- Плагин в IDE подхватывает изменения файла сам.
- Хочется, чтобы Claude реагировал на каждый комментарий сразу, — для этого есть `/review_live`.
- Если из ответов пользователя появился архитектурный инсайт (почему в проекте принято делать X, неочевидное правило,
  решение) — добавь его в `CLAUDE.md` проекта. Только из слов пользователя, ничего не додумывай.
